**Решения (утверждено 2026-07-24):** модель — коды активации + кнопка «Хочу план» (лиды в

(тот же план → срок прибавляется к expires_at, другой план → новая подписка с даты
активации, остаток сгорает).

## Контекст (Беларусь)

Оплата — целиком **вне системы**: B2B-стандарт РБ — счёт → банковский перевод → акт
(документы вручную, вне скоупа v1). Stripe/PayPal недоступны, ЮKassa — РФ; локальные
карточные шлюзы (bePaid/WebPay) и ЕРИП — возможная фаза 2, только после подтверждения
спроса. Код полностью развязывает оплату и активацию: заплатил любым способом (перевод,
наличные, через дилера) → получил код → активировал. Коды же работают как промо и канал
продаж через посредников.

## Модель данных (2 таблицы + 1 колонка)

### `license_codes`
- `id` UUID PK
- `code` TEXT NOT NULL UNIQUE — формат `XXXX-XXXX-XXXX` (12 симв., алфавит A–Z/2–9 без
  похожих 0/O/1/I; crypto-random, ~57 бит — достаточно при строгом rate-limit активации)
- `plan_id` UUID NOT NULL REFERENCES plans(id)
- `duration_days` INT NOT NULL CHECK (> 0)
- `status` TEXT NOT NULL DEFAULT 'issued' CHECK IN ('issued', 'activated', 'revoked')
- `note` TEXT — кому/зачем выписан (видит только админ)
- `issued_by_account_id` UUID REFERENCES accounts(id)
- `activated_by_account_id` UUID REFERENCES accounts(id), `activated_at` TIMESTAMPTZ
- `created_at`/`updated_at`

### `plan_requests` (лиды «Хочу план»)
- `id` UUID PK, `account_id` UUID NOT NULL REFERENCES accounts(id) ON DELETE CASCADE
- `plan_id` UUID NOT NULL REFERENCES plans(id)
- `comment` TEXT — свободный текст владельца (телефон/пожелания)
- `status` TEXT NOT NULL DEFAULT 'new' CHECK IN ('new', 'processed')
- `created_at`, `processed_at`

### `accounts.is_platform_admin`
- BOOLEAN NOT NULL DEFAULT false. Выставляется вручную (SQL) владельцу платформы. Это
  **первый выход за tenant-модель** — см. «Безопасность».

Одна миграция, обратимая. schema.sql — синхронно.

## Безопасность (критичные места)

1. **Гард платформенного админа** — `requirePlatformAdmin`: проверяет флаг **из БД на каждый
   запрос** (не из JWT — привилегия не должна жить в токене и переживать снятие флага).
   Отдельный роутер `/api/admin/*`, НЕ проходит через nursery-скоуп; на нём строгий
   rate-limit.
2. **Активация — атомарная**, гонка двойной активации исключается на уровне БД:
   `UPDATE license_codes SET status='activated', activated_by_account_id=?, activated_at=now()
   WHERE code=? AND status='issued' RETURNING *` — 0 строк → «код недействителен или уже
   использован» (не различать наружу, чтобы не давать оракул перебору).
3. **Rate-limit на активацию** — строгий (по образцу authLimiter: ~10 попыток / 15 мин на
   IP): 12-символьный код + лимит = перебор нереален.
4. **Аудит**: выпуск, активация, revoke, обработка лида — в `activity_logs`.
5. Нормализация ввода кода: upper-case, убрать дефисы/пробелы.

## Логика активации (одна транзакция + существующий lockAccount)

```
POST /api/subscriptions/activate-code { code }   (requireAuth, только owner-токен)
```
1. Нормализовать код → атомарный UPDATE (см. выше) → плана нет/неактивен → откат.
2. `lockAccount(trx, accountId)` (существующий advisory-lock).
3. Текущая активная подписка (`getActiveWithPlan`):
   - **тот же план и есть `expires_at`** → `expires_at += duration_days` (стакание;
     продление заранее не сжигает дни);
   - **иначе** (trial, free, другой план) → текущую в `cancelled`, создать новую `active`
     с `expires_at = now() + duration_days`. Partial-unique `uq_subscriptions_active_account`
     страхует от второй active.
4. Ответ — новая подписка (форма как `/subscriptions/current`).
5. Уведомление владельцу (новый тип `subscription.activated` → константы + миграция CHECK
   `chk_notifications_type`, порядок из D7) + activity_logs.
6. Существующий cron `expireOverdue` работает без изменений (истёкшая платная → free).

## Лиды «Хочу план»

```
POST /api/plan-requests { planId, comment? }   — owner; не чаще 1 открытой заявки на план
GET  /api/plan-requests/my                     — свои заявки со статусами
```
На странице тарифов: кнопка у плана → форма (комментарий/контакт) → «Заявка отправлена, мы
свяжемся». Плюс статический блок «Как оплатить» (контакты/реквизиты — текст в конфиге
фронта, не в БД).

## Админ-API (`/api/admin/*`, requirePlatformAdmin)

```
POST /api/admin/license-codes            { planId, durationDays, note?, count? (1..50) }
GET  /api/admin/license-codes            ?status=&page=&perPage=   (+ email активировавшего)

GET  /api/admin/plan-requests            ?status=new  (+ email аккаунта, план)
POST /api/admin/plan-requests/:id/process
```

## Тесты (ключевые)

- Активация: валидный код → план/срок; невалидный/чужой формат → 404-одинаковый;
  повторная активация того же кода → отказ; **гонка** — два параллельных запроса с одним
  кодом → ровно одна активация (по образцу concurrencyLimits.test.js);
- стакание: тот же план → expires_at увеличился на duration; другой план → новая подписка
  с now(), старая cancelled; активация на trial/free → новая active;
- revoked-код → отказ; код неактивного плана → отказ;
- rate-limit активации → 429;
- админ: без флага → 403 (owner обычного аккаунта), с флагом → работает; снятие флага в БД
  действует немедленно (следующий запрос → 403, токен тот же);
- лиды: создание/дубль открытой заявки на тот же план → 409; process админом;
- изоляция: админ-ручки не зависят от nursery-контекста; обычные ручки не отдают чужие лиды.

## Критерии приёмки

- Полный цикл руками: сгенерил код в админке → активировал на тестовом аккаунте → план и
  `expires_at` корректны → cron истечения переводит на free.
- Ни одного пути двойного использования кода (тест гонки зелёный).
- Обычный пользователь не видит и не достаёт админ-ручки (403) и чужие коды/лиды.
- Покрытие не ниже порогов 90/80.
