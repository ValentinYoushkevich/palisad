**Статус:** ✅ РЕАЛИЗОВАНО (2026-07-25, Э1–Э7). One-shot сессии (POST со серверным diff по
поддереву локаций, идемпотентность по clientRequestId), apply (батч движений write-off/transfer

Бэкенд-сьют 554 теста, coverage 96.31% stmts / 89.46% branch; фронт 118 тестов; живая приёмка
`MODULE 20 «Инвентаризация»` в acceptance-check.mjs — PASS (12/12), overall ИТОГО 133/134
(единственный FAIL — известный pre-existing M4#4). **Зависимости:** нет (переиспользует сканер, локации,
движения, офлайн-очередь, pdfkit).
**Решения (утверждено 2026-07-24):** роли разделены — сканирует и завершает worker+,

только фиксируются в акте, без формы заведения; параллельные сессии разрешены (пересечение
зон — предупреждение, не блокировка); PDF-акт — в v1.

## Ключевое архитектурное решение: one-shot сессия

Сессия «в процессе» живёт **только на устройстве** (Dexie). На сервер уходит **одним POST'ом
уже завершённая** сессия целиком (зона, времена, все сканы, clientRequestId). Сервер её
сохраняет, считает **авторитетный diff** и фиксирует снапшот.

Почему так: нет промежуточного состояния на сервере → нет reconcile локальных id сканов, нет
конфликтов «двое пишут в одну сессию», offline тривиален (тот же паттерн, что create_operation
в очереди). Минус — прогресс не виден с других устройств до завершения; для v1 приемлемо.

## Поток

1. **Старт (устройство, офлайн-ок).** Worker: «Инвентаризация» → выбор зоны (любой уровень
   иерархии: участок/секция/ряд/место). Если по локальному кэшу видна другая незавершённая
   сессия с пересекающейся зоной — предупреждение (продолжить можно).
2. **Скан-режим.** Переиспользуем `QrScanner.vue`. Каждый скан: резолв по локальному кэшу
   растений (nursery-scoped) → счётчик «отсканировано N»; дубль кода в сессии — игнор +
   короткий сигнал; ручной ввод numeric_code — для нечитаемых этикеток. Всё копится в Dexie.
3. **Завершение (устройство).** Локальный **предварительный** diff по кэшу → экран
   результатов сразу, без сети. Сессия ставится в очередь синка (новый тип
   `create_inventory_session`, payload one-shot, идемпотентность по clientRequestId — как F2).
4. **Синк.** Сервер: сохранить сессию+сканы, посчитать авторитетный diff (по актуальной БД),
   зафиксировать снапшот. Reconcile на устройстве: локальная сессия заменяется серверной.
5. **Применение (онлайн, owner/agronomist).** Экран сессии: категории diff с чекбоксами →
   «Списать выбранные» (выбор типа движения с `sets_status='written_off'` — причина, см.
   отчёт «Отпад»), «Переместить сюда выбранных чужих». Применение — серверный batch, не
   через офлайн-очередь: действия по устаревшему локальному diff недопустимы.
6. **Акт PDF** — в любой момент после синка.

## Diff (считает сервер при приёме, снапшот сохраняется)

Зона = поддерево выбранной локации (собрать id потомков в сервисе по `locations.parent_id` —
дерево питомника небольшое). Учитываются активные растения (`deleted_at IS NULL`, статус
`growing`/`storage`).

| Категория | Условие | Действие из diff |
|---|---|---|
| `matched` | отсканирован, локация в зоне | нет (свёрнуто, счётчик) |
| `missing` | числится в зоне, не отсканирован | списание (выбранных) |
| `foreign` | отсканирован, растение питомника, но локация вне зоны/NULL | перемещение в зону |
| `unknown` | код не найден в питомнике (поиск nursery-scoped, D8) | нет — только в акте |

## Модель данных (1 миграция, обратимая; schema.sql синхронно)

### `inventory_sessions`
- `id` UUID PK, `nursery_id` UUID NOT NULL FK CASCADE, `location_id` UUID NOT NULL FK
- `user_id` UUID FK (кто сканировал), `started_at`/`completed_at` TIMESTAMPTZ NOT NULL
- `client_request_id` TEXT + partial-unique (идемпотентность replay, образец F2)
- снапшот счётчиков: `matched_count`, `missing_count`, `foreign_count`, `unknown_count` INT
- `created_at`/`updated_at`

### `inventory_items` (строки diff, включая missing)
- `id` UUID PK, `session_id` UUID NOT NULL FK CASCADE
- `plant_id` UUID NULL FK SET NULL (NULL для unknown), `raw_code` TEXT NULL (NULL для missing)
- `category` TEXT CHECK IN ('matched','missing','foreign','unknown')
- `scanned_at` TIMESTAMPTZ NULL (NULL для missing)
- `applied_movement_id` UUID NULL FK SET NULL — чем закрыт (аудит применения)

Лимит: ≤ 5000 сканов на сессию (валидация; больше — делить зону).

## API

Все под `requireAuth` + `requireNurseryAccess`.

```
POST /api/nurseries/:nurseryId/inventory-sessions          WRITE_ROLES (worker+)
  { locationId, startedAt, completedAt, clientRequestId,
    scans: [{ code, scannedAt }] }                          → сессия + diff (категории)
GET  /api/nurseries/:nurseryId/inventory-sessions           список, пагинация (parsePagination)
GET  /api/nurseries/:nurseryId/inventory-sessions/:id       детали + items по категориям
POST /api/nurseries/:nurseryId/inventory-sessions/:id/apply STRUCTURE_ROLES, онлайн
  { writeOff: { plantIds: [], movementTypeId },             → создаёт движения батчем
    transfer: { plantIds: [] } }                              в транзакции
GET  /api/nurseries/:nurseryId/inventory-sessions/:id/act.pdf   PDF-акт
```

`apply`: перед каждым движением перепроверяет актуальное состояние растения (жив, статус,
текущая локация); несоответствующие — пропускает и возвращает `skipped[]` с причинами.
Повторный apply по уже закрытым items — идемпотентный скип (`applied_movement_id` стоит).
Движения — существующим механизмом (`sets_status` отработает статусы, история движений цела).

## Офлайн (frontend)

- Dexie: таблица `inventory_sessions_local` (localId, locationId, startedAt, scans[],
  status `scanning/completed`). Сканы — массив в записи сессии (тысячи — ок для Dexie).
- Новый тип очереди `create_inventory_session` в `syncQueue.constants` + обработчик в
  `useSyncManager` (payload несёт nurseryId — F7; идемпотентность — clientRequestId — F2;
  404/409 обрабатываются по образцу существующих типов).
- Reconcile: после успешного POST локальная сессия удаляется, серверная (с авторитетным
  diff) кэшируется для просмотра.
- Локальный diff-превью считается тем же алгоритмом по кэшу растений — функция выносится в
  общий модуль и покрывается юнитом отдельно от серверной (две реализации — JS/SQL — один
  набор тест-кейсов).
- Применение и PDF — только онлайн (кнопки задизейблены офлайн с подсказкой).

## PDF-акт

По образцу labels (pdfkit, кириллический шрифт уже подключён): шапка питомника, зона, кто
сканировал, период, счётчики по категориям, таблицы расхождений (missing: код/вид/локация;
foreign: код/вид/где числится; unknown: сырой код), строка «применено: N списано, M
перемещено» если apply был. Стрим в ответ (как labels).

## Тесты (ключевые)

- diff: каждая категория; растение в под-поддереве зоны → matched; soft-deleted не
  учитывается; чужой QR того же аккаунта (другой питомник) → unknown (изоляция D8);
- идемпотентность POST по clientRequestId (replay из очереди → та же сессия, не дубль);
- apply: движения создаются, sets_status отрабатывает; растение изменившееся между diff и
  apply → skipped с причиной; повтор apply → 0 новых движений; worker → 403;
- лимит 5000 → 400; пагинация списка;
- изоляция: сессии/акты чужого питомника → 404 (существующая матрица);
- фронт: дубль скана игнорится; офлайн-завершение → элемент очереди с nurseryId и
  clientRequestId; reconcile заменяет локальную сессию.

## Критерии приёмки

- Полный цикл офлайн: старт → сканы без сети → завершение → превью-diff → появилась сеть →
  синк → серверный diff совпал на неизменных данных.
- Apply никогда не создаёт дубль движения (тест гонки + повтор).
- PDF открывается, кириллица цела, счётчики сходятся с diff.
- Покрытие ≥ порогов 90/80; изоляция tenant'ов покрыта тестами.

## Связь с v2-роадмапом

В роадмапе инвентаризации нет — фича добавлена v3. Конфликтов нет: работает по поддереву
локаций любого типа, поэтому этап 7 роадмапа («склад/зимовка» = новые типы локаций)
поддержится автоматически, а движения списания/перемещения — существующий механизм, на
который этап 4 (себестоимость) навешивает свои пересчёты независимо.
