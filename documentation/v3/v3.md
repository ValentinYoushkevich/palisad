# Палисад v3 — концепции развития

**Дата:** 2026-07-24. **Статус:** концепт, утверждён к проработке. План реализации — отдельным
шагом на основе этого документа.

Контекст: v2 (мультипитомник, офлайн-ядро, RBAC, стадии производства, подписки) закрыт,
аудит пройден полностью. v3 — переход от «журнала учёта» к инструменту, за который платят:
отчёты, биллинг, инвентаризация, экспорт. Плюс один инфраструктурный задел (фото → MinIO).

Приоритет (по бизнес-ценности): 1) отчёты, 2) биллинг, 3) инвентаризация, 4) экспорт,
5) MinIO — по триггеру, не по расписанию.

**Связь с v2-роадмапом** (`../v2-roadmap-proposal.md`): его этапы 1–3 выполнены в v2. v3
встраивается перед этапом 4: отчёты v3 = этап 5.1 + часть 5.2 (нормо-часы, без денег —
роадмап это явно допускает), экспорт = этап 5.4 (флаг `feature_export`), биллинг и
инвентаризация — новые, конфликтов не создают. В очереди роадмапа после v3 остаются:
этап 4 (себестоимость в деньгах — `cost_entries`), 5.3 (рентабельность), 6 (задачи),
7 (склад/зимовка), 8 (CRM; `species_prices` из v3-экспорта станет источником дефолтной
цены при оформлении продажи). Детали разграничения — в планах 01/03/04.

## 1. Отчёты и аналитика

**Проблема.** Система собирает операции, движения, стадии, нормы труда — но не отвечает ни на
один вопрос владельца. Учёт ради учёта не продаётся; продаётся ответ «сколько стоит вырастить
тую до 3 лет» и «какой отпад по партии».

**Ценность.** Превращает накопленные данные в аргумент для оплаты подписки. Все исходные
данные уже в БД — фича почти целиком читающая (низкий риск).

### 1.1. Отчёт «Отпад» (списания/гибель)

- Разрез: период × локация (участок/секция) × вид × стадия.
- Источник: движения с `sets_status = 'written_off'` + операции, история стадий.
- Метрики: количество списанных, % от числившихся на начало периода, динамика по месяцам.
- Ответ на вопрос: «где и на какой стадии мы теряем растения».

### 1.2. Отчёт «Себестоимость выращивания» (по нормам труда)

- Источник: `stage_labor_norms` (норма минут на операцию × стадия) × фактические операции
  растения/партии + длительность пребывания в стадиях (`plant_stage_history`).
- Расчёт: сумма нормо-минут по операциям растения; агрегат по виду/стадии — «средняя
  трудоёмкость туи от прививки до реализации: N нормо-часов».
- Опционально (фаза 2): стоимость нормо-часа в настройках питомника → себестоимость в деньгах.
- Ответ: «во что обходится растение до продажи», «какая культура съедает труд».

### 1.3. Отчёт «Движение остатков»

- Разрез: период × локация × вид × стадия.
- Формула: остаток на начало + приход (создание/arrival) − продажа − списание ± перемещения
  между локациями = остаток на конец.
- Источник: `plants` (created_at, status, deleted_at) + `movements`.
- Ответ: «сколько чего стоит на участках и как менялось за сезон».

### 1.4. Требования (общие для отчётов)

- Только чтение; RBAC — owner/agronomist (observer — по решению позже).
- Все запросы строго nursery-scoped (существующая изоляция).
- API: `GET /api/nurseries/:nurseryId/reports/<name>` с параметрами периода/разреза; Zod на
  параметры, пагинация не нужна (агрегаты), но период ограничить (например, ≤ 2 лет).
- UI: страница «Отчёты», таблицы + простые графики; экспорт каждого отчёта в CSV (см. §4 —
  единый механизм экспорта).
- Производительность: агрегаты по индексированным полям (индексы D6 уже есть); при росте —
  materialized view, но не в первой итерации.
- Офлайн: отчёты — онлайн-фича (первая в системе). Явно показать «нет сети — отчёты
  недоступны», в очередь ничего не ставить.

## 2. Биллинг

**Проблема.** Trial 14 дней → downgrade на free. Заплатить невозможно в принципе
(`changePlan` → 403): воронка ведёт в никуда.

**Ценность.** Замыкает монетизацию. Без него всё остальное — благотворительность.

### 2.1. Фаза 1 — ручные инвойсы (минимум, быстро)

- Владелец жмёт «Перейти на план X» → создаётся заявка (`billing_requests`: account_id,
  plan_id, статус `pending/approved/rejected`, комментарий).
- Уведомление админу платформы (пока — вручную по списку заявок), оплата вне системы
  (счёт/перевод).
- Админ подтверждает заявку → подписка `active` с `expires_at` (+30/365 дней), существующий
  cron `expireOverdue` продолжает работать как есть.
- Нужна **роль платформенного админа** (superadmin вне tenant-модели) и минимальная
  админ-страница списка заявок. Это первый выход за пределы tenant-мира — спроектировать
  аккуратно (отдельный гард, не смешивать с nursery-RBAC).
- `changePlan` остаётся закрытым для прямого вызова; открывается только путь «заявка →
  подтверждение».

### 2.2. Фаза 2 — платёжный провайдер (после первых платящих)

- Провайдер согласовать отдельно (ЮKassa/Stripe — зависит от юрисдикции клиентов).
- Вебхуки оплаты → автоактивация подписки; заявки фазы 1 остаются как fallback.
- Не проектировать заранее глубже этого пункта — сначала подтвердить спрос фазой 1.

### 2.3. Требования

- История заявок/активаций — в `activity_logs` (или отдельная таблица биллинг-событий).
- Идемпотентность подтверждения (повторный клик админа не создаёт вторую подписку —
  partial-unique `uq_subscriptions_active_account` уже защищает, обработать конфликт).
- Уведомление владельцу о подтверждении (существующий механизм notifications, новый тип →
  правка констант + миграция CHECK, см. D7).

## 3. Инвентаризация сканером

**Проблема.** Учёт разъезжается с реальностью за сезон: растения гибнут, переставляются без
отметки. Ручная сверка тысяч растений — дни работы.

**Ценность.** Сверка ряда — за минуты прогулки со смартфоном. Фича находит потерянные деньги
клиента; почти вся инфра готова (сканер, локации, движения, офлайн-очередь).

### 3.1. Сценарий

1. Работник открывает «Инвентаризация», выбирает зону охвата (участок/секция/ряд).
2. Режим массового скана: сканирует QR подряд, приложение копит список (счётчик «отсканировано
   N»), карточки не открывает. Дубль скана — игнор с коротким сигналом. Ручной ввод
   numeric_code — для нечитаемых этикеток.
3. Завершение → **diff с учётом** по выбранной зоне:
   - **не найдено** — числится в зоне, не отсканировано (кандидат в списание/розыск);
   - **чужие** — отсканировано здесь, по учёту в другой локации (кандидат на перемещение);
   - **неизвестные QR** — кода нет в базе питомника (кандидат на заведение);
   - **совпало** — числится и найдено (свернуть, показывать счётчик).
4. Массовые действия из diff: списать выбранные «не найденные» (движение write_off), принять
   «чужих» (движение transfer в эту локацию), завести неизвестных.
5. Акт инвентаризации: PDF (существующий pdfkit-механизм этикеток) — зона, дата, исполнитель,
   итоги по категориям, список расхождений.

### 3.2. Модель данных (набросок)

- `inventory_sessions`: id, nursery_id, location_id (корень зоны), user_id, status
  (`in_progress/completed/cancelled`), created_at/completed_at.
- `inventory_scans`: session_id, plant_id (nullable для неизвестных), raw_code, scanned_at.
- Diff считается на завершении (или на лету) сравнением сканов с `plants` зоны
  (location-поддерево, существующая иерархия локаций).

### 3.3. Офлайн

- Скан-режим обязан работать без сети (поле!): сканы копятся в IndexedDB, сверка по локальному
  кэшу растений; завершение сессии и массовые действия — через существующую очередь синка
  (типы `create_movement` переиспользуются; новая — фиксация сессии).
- Конфликт «растение изменено с другого устройства между сканом и синком» — принять
  last-write-wins как во всём остальном синке, отметить в акте.

### 3.4. RBAC

- Сканировать — все пишущие роли (worker+); массовые списания из diff — STRUCTURE_ROLES
  (владелец/агроном), как обычный delete/write_off.

## 4. Экспорт прайса/остатков

**Проблема.** Продажа — конечная цель питомника; данные об остатках заперты в системе.

**Ценность.** Питомник ведёт прайс в Excel руками — экспорт убирает ручную работу и делает
систему источником истины для витрины.

### 4.1. Объём

- Экспорт **остатков**: активные растения (не проданы/не списаны) агрегированно — вид, сорт,
  стадия, контейнер, количество, локация (опционально). Формат: CSV (Excel-совместимый,
  UTF-8 BOM, `;`-разделитель — согласовать при реализации).
- Экспорт **прайса**: то же + цена. Цены в системе нет → минимальное расширение: прайс-колонка
  на уровне «вид × контейнер» (или «вид × стадия») в справочнике питомника. Без сложных
  прайс-листов/скидок в первой итерации.
- Экспорт отчётов из §1 — тем же механизмом (единый CSV-эндпоинт-паттерн
  `GET .../reports/<name>?format=csv`).

### 4.2. Требования

- Стрим-выгрузка (не собирать всё в памяти), лимит строк разумный (питомник — десятки тысяч
  позиций максимум, не проблема).
- RBAC: owner/agronomist.
- Онлайн-фича (как отчёты).
- Интеграции с маркетплейсами — вне скоупа v3; сначала CSV.

## 5. Инфраструктура: фото → MinIO (по триггеру)

**Решение (2026-07-24):** облачные S3-провайдеры **не используем** — self-hosted **MinIO**
контейнером в docker-compose рядом с Postgres. Данные остаются у нас.

**Текущее состояние:** байты фото в Postgres (bytea, лимит 512 КБ, стрим через backend с
tenant-гардами). Для старта — осознанно и правильно (транзакционность, простота).

**Чем плохо при росте:** таблица фото раздувает БД (backup/restore/миграции тяжелеют, WAL
таскает байты), каждый показ фото ест коннект БД и память backend.

**Целевая схема:**
- MinIO-сервис в docker-compose (volume, креденшалы из env — по образцу B34), бакет на
  окружение.
- В Postgres остаётся только мета (id, operation_id, mime, size, storage_key) — таблица уже
  почти такая, добавится `storage_key` вместо байтов.
- Отдача — через backend-proxy (существующие tenant-гарды сохраняются как есть; presigned-URL
  не нужны, наружу MinIO не светим — только внутренняя сеть compose).
- Миграция постепенная: новые фото — в MinIO, старые — фоновым переливом, колонка bytea
  дропается после переноса.

**Триггер переезда (не делать раньше):** таблица фото > ~5 ГБ, или заметная деградация API
из-за отдачи фото, или потребность в фото > 512 КБ. До триггера — bytea остаётся.
