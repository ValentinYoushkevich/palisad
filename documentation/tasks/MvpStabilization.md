# MvpStabilization — стабилизация MVP перед стартом v2

**Создано:** 2026-06-12 · **Статус:** выполнено · **Прогон верификации:** 2026-06-13

## Чего хотим достичь

Формально подтвердить, что MVP (v1) действительно готов: критерии приёмки всех модулей
сверены, сквозной сценарий проходит, офлайн-цикл работает, репозиторий имеет нормальный
README. После этого можно со спокойной совестью стартовать v2 (Этап 1 — несколько питомников).

Покрывает 4 чекбокса блока «1. Стабилизация MVP» из [`CURRENT_TASKS.md`](CURRENT_TASKS.md).

## План

1. **Поднять окружение**: Docker (Postgres из `docker-compose.yml`), `npm run migrate` + `npm run seed`,
   запустить backend локально (`npm run dev`/`start`).
2. **Критерии приёмки модулей 2–13**: пройти таблицы «Критерии приёмки» в
   `backend/documentation/modules/MODULE_2..13.md`. Проверка двух видов:
   - runtime — через HTTP-запросы к запущенному API (auth-флоу, CRUD, RBAC, лимиты, PDF);
   - статическая — сверка кода/схемы там, где runtime-проверка избыточна (структура таблиц,
     наличие индексов, cron).
   По факту прохождения — проставить «Реализовано» в конце соответствующего `MODULE_N.md`;
   найденные расхождения фиксировать здесь и чинить, если это баг кода (не дока).
3. **Сквозной smoke-сценарий** (API-уровень): регистрация → питомник → сотрудник → растение
   с видом через GBIF → операция с фото → движение → этикетка PDF → лента активности.
   Один последовательный прогон, результат каждого шага фиксируется.
4. **Офлайн-цикл**: код-ревью цепочки `useSyncManager` → `syncQueue.service` (frontend):
   постановка в очередь офлайн, отправка при появлении сети, «сервер побеждает» при конфликте,
   `retries >= 3 → failed` + Toast. Браузерная часть (Service Worker, DevTools) — отметить,
   что именно проверено кодом, а что требует ручного теста в браузере.
5. **README.md**: запуск через docker-compose, локальный dev-режим (backend + frontend),
   миграции/сиды, переменные окружения, структура репозитория.
6. По итогам — проставить чекбоксы в `CURRENT_TASKS.md`, дописать раздел «Результаты» сюда.

### 4. Офлайн-цикл

Код-ревью цепочки `useSyncManager.js` → `syncQueue.service.js` (соответствует
acceptance-таблице `frontend/documentation/modules/MODULE_12.md`).

**Проверено кодом:**

- Постановка в очередь: `addToQueue` пишет в `sync_queue` со `status='pending'`, `retries=0`.
- Авто-обработка при появлении сети: `watch(isOnline)` → `processQueue()` (M12#1).
- Порядок синка: `processQueue` сперва шлёт не-фото (операции/движения), затем фото (M12#8).
- `retries >= 3 → failed` + Toast: `markFailed` инкрементит `retries`, при `>=3` ставит
  `status='failed'`; `processItem` после `markFailed` читает запись через `getById` и при
  статусе `failed` показывает Toast «Не удалось отправить после 3 попыток» (M12#4).
- Ручной повтор: `retryFailed` сбрасывает `retries=0`, `status='pending'` (M12#5).
- Фото после операции: `processPhotoItem` грузит фото отдельным шагом после операции (M12#6).

**Багфикс (внесён в этой задаче):** проверка «стал ли элемент `failed`» раньше делалась через
`getPending().find(...)`, но `getPending` возвращает только `pending`-элементы — только что
ставший `failed` элемент в выборку не попадал, и Toast не показывался. Добавлен
`syncQueue.service.getById(id)` и точечное чтение в `useSyncManager.processItem`.

**Требует ручного теста в браузере (Service Worker / DevTools, кодом не проверяемо):**

- M12#2/#3 — UI `SyncStatusBadge` и кнопка ручной синхронизации (реальное переключение сети).
- M12#1 — фактическая постановка офлайн при отключённой сети через Service Worker.

**Находка по критерию M12#7 («конфликт: серверная версия побеждает»):** в коде отсутствует
механизм разрешения конфликтов — нет поля версии / `updated_at`-guard, `updateOperation`
на бэке делает обычный `update` без проверки устаревания. Офлайн-правка переигрывается как
обычный `PATCH`, то есть фактически побеждает запись синкающего клиента (last-write-wins),
а не сервер. «Сервер побеждает» выполняется лишь в слабом смысле: отклонённая бизнес-правилом
мутация (например, растение уже продано → `400/404`) не форсит свою версию, а уходит в `failed`
после 3 попыток, и серверные данные перечитываются при перезагрузке. Полноценный server-wins
для конкурентного редактирования одного поля — задача v2 (требует версионирования сущностей).

### Findings (расхождения дока ↔ код)

1. **M4#4** — `rbac.js` мёртвый код; RBAC через middleware. Критерий доки устарел. (зафиксировано в `MODULE_4.md`)
2. **Staff-логин отсутствует в API** — сотрудники (agronomist/worker/observer) не логинятся через
   `/auth/login`; в приёмочном скрипте их сессии подписываются сервером напрямую (`forgeSession`).
3. **M12#7 server-wins не реализован** — нет разрешения конфликтов; де-факто last-write-wins (см. п.4 выше).
